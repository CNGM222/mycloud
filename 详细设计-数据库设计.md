# 详细设计-数据库设计

## 1. 设计目标

数据库用于保存用户、文件目录、文件元数据、文件内容、任务记录和操作日志。后端通过 JDBC 和 HikariCP 访问 MySQL 9.6，所有客户端不得直接连接数据库。

## 2. 数据库命名

建议数据库名：

```sql
CREATE DATABASE mycloud DEFAULT CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci;
USE mycloud;
```

## 3. 表结构 SQL

### 3.1 users

```sql
CREATE TABLE users (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  username VARCHAR(64) NOT NULL,
  email VARCHAR(128) NOT NULL,
  password_hash VARCHAR(255) NOT NULL,
  role VARCHAR(32) NOT NULL DEFAULT 'user',
  total_capacity BIGINT NOT NULL DEFAULT 10737418240,
  used_capacity BIGINT NOT NULL DEFAULT 0,
  status VARCHAR(32) NOT NULL DEFAULT 'normal',
  created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  CONSTRAINT uk_users_username UNIQUE (username),
  CONSTRAINT uk_users_email UNIQUE (email),
  CONSTRAINT ck_users_role CHECK (role IN ('user', 'admin')),
  CONSTRAINT ck_users_status CHECK (status IN ('normal', 'disabled')),
  CONSTRAINT ck_users_capacity CHECK (total_capacity >= 0 AND used_capacity >= 0 AND used_capacity <= total_capacity)
);
```

字段说明：

| 字段 | 说明 |
| --- | --- |
| username | 登录名，唯一 |
| email | 邮箱，唯一 |
| password_hash | BCrypt 哈希 |
| role | 用户角色 |
| total_capacity | 总容量，单位字节 |
| used_capacity | 已用容量，单位字节 |
| status | 账号状态 |

### 3.2 files

```sql
CREATE TABLE files (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  user_id BIGINT NOT NULL,
  parent_id BIGINT NULL,
  name VARCHAR(255) NOT NULL,
  type VARCHAR(16) NOT NULL,
  mime_type VARCHAR(128) NULL,
  size BIGINT NOT NULL DEFAULT 0,
  content_id BIGINT NULL,
  md5 VARCHAR(64) NULL,
  extension VARCHAR(32) NULL,
  created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  CONSTRAINT fk_files_user FOREIGN KEY (user_id) REFERENCES users(id),
  CONSTRAINT fk_files_parent FOREIGN KEY (parent_id) REFERENCES files(id),
  CONSTRAINT ck_files_type CHECK (type IN ('file', 'folder')),
  CONSTRAINT ck_files_size CHECK (size >= 0),
  CONSTRAINT uk_files_same_dir_name UNIQUE (user_id, parent_id, name)
);

CREATE INDEX idx_files_user_parent ON files(user_id, parent_id);
CREATE INDEX idx_files_user_name ON files(user_id, name);
CREATE INDEX idx_files_user_type ON files(user_id, type);
CREATE INDEX idx_files_updated_at ON files(updated_at);
```

设计说明：

- `parent_id IS NULL` 表示根目录下的文件或文件夹。
- `type='folder'` 时 `size=0`，`content_id`、`md5`、`extension` 可为空。
- 同一用户同一目录下名称不可重复。

### 3.3 file_contents

```sql
CREATE TABLE file_contents (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  file_id BIGINT NOT NULL,
  content LONGBLOB NOT NULL,
  size BIGINT NOT NULL,
  md5 VARCHAR(64) NOT NULL,
  created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  CONSTRAINT fk_file_contents_file FOREIGN KEY (file_id) REFERENCES files(id),
  CONSTRAINT uk_file_contents_file UNIQUE (file_id),
  CONSTRAINT ck_file_contents_size CHECK (size >= 0)
);
```

设计说明：

- 文件内容存储在 `content` 字段。
- 后端写入和读取必须使用 JDBC 流式 API。
- `file_contents.file_id` 与 `files.id` 一对一。
- `files.content_id` 不设置数据库外键，避免与 `file_contents.file_id` 形成循环外键；一致性由上传事务和服务层维护。

### 3.4 tasks

```sql
CREATE TABLE tasks (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  user_id BIGINT NOT NULL,
  file_id BIGINT NULL,
  task_type VARCHAR(16) NOT NULL,
  client_type VARCHAR(16) NOT NULL,
  status VARCHAR(32) NOT NULL,
  progress INT NOT NULL DEFAULT 0,
  error_message VARCHAR(512) NULL,
  created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  CONSTRAINT fk_tasks_user FOREIGN KEY (user_id) REFERENCES users(id),
  CONSTRAINT fk_tasks_file FOREIGN KEY (file_id) REFERENCES files(id) ON DELETE SET NULL,
  CONSTRAINT ck_tasks_type CHECK (task_type IN ('upload', 'download')),
  CONSTRAINT ck_tasks_client CHECK (client_type IN ('web', 'windows', 'android')),
  CONSTRAINT ck_tasks_status CHECK (status IN ('pending', 'running', 'success', 'failed', 'cancelled')),
  CONSTRAINT ck_tasks_progress CHECK (progress >= 0 AND progress <= 100)
);

CREATE INDEX idx_tasks_user_created ON tasks(user_id, created_at);
CREATE INDEX idx_tasks_user_status ON tasks(user_id, status);
```

### 3.5 operation_logs

```sql
CREATE TABLE operation_logs (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  user_id BIGINT NULL,
  action VARCHAR(64) NOT NULL,
  target_id BIGINT NULL,
  target_type VARCHAR(32) NULL,
  client_type VARCHAR(16) NOT NULL,
  ip_address VARCHAR(64) NULL,
  created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  CONSTRAINT fk_operation_logs_user FOREIGN KEY (user_id) REFERENCES users(id),
  CONSTRAINT ck_operation_logs_client CHECK (client_type IN ('web', 'windows', 'android'))
);

CREATE INDEX idx_logs_user_created ON operation_logs(user_id, created_at);
CREATE INDEX idx_logs_action_created ON operation_logs(action, created_at);
```

## 4. 枚举值

| 字段 | 可选值 |
| --- | --- |
| users.role | user, admin |
| users.status | normal, disabled |
| files.type | file, folder |
| tasks.task_type | upload, download |
| tasks.client_type | web, windows, android |

## 5. 事务设计

### 5.1 上传文件事务

同一事务内执行：

1. 锁定用户容量记录。
2. 校验剩余容量。
3. 插入 `files` 元数据，`content_id` 暂为空。
4. 使用 JDBC 流式写入 `file_contents.content`。
5. 回写 `files.content_id`。
6. 增加 `users.used_capacity`。
7. 写入 `tasks` 和 `operation_logs`。
8. 提交事务。

任一步失败则回滚，不能留下无效文件记录。

### 5.2 删除文件事务

同一事务内执行：

1. 查询待删除节点及所有子节点。
2. 校验所有节点属于当前用户。
3. 统计待释放容量。
4. 删除相关 `file_contents`。
5. 按子节点优先顺序删除相关 `files`。
6. 减少 `users.used_capacity`。
7. 写入 `operation_logs`。
8. 提交事务。

### 5.3 移动文件事务

同一事务内执行：

1. 查询源节点。
2. 查询目标文件夹。
3. 校验归属和层级合法性。
4. 校验目标目录名称不冲突。
5. 更新源节点 `parent_id`。
6. 写入 `operation_logs`。

## 6. JDBC 流式读写要求

上传写入：

- 使用 `PreparedStatement#setBinaryStream` 写入 `LONGBLOB`。
- 不允许将完整文件读取到 `byte[]` 后再写入。
- 需要在事务内完成元数据和内容写入。

下载读取：

- 使用 `ResultSet#getBinaryStream` 读取 `LONGBLOB`。
- 将输入流分块写入 HTTP 响应输出流。
- 下载过程不修改文件内容。

## 7. 数据初始化

建议初始化管理员账号：

```sql
INSERT INTO users (
  username, email, password_hash, role, total_capacity, used_capacity, status
) VALUES (
  'admin', 'admin@example.com', '<BCryptHash>', 'admin', 107374182400, 0, 'normal'
);
```

实际密码哈希由后端工具生成，不在 SQL 中保存明文密码。
